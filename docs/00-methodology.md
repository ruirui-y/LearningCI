# 00. LearningCI 方法论

## 1. 问题定义

LearningCI 解决的不是“如何获得更多学习资料”，而是三个更具体的问题：

### 1.1 假进度

学习者很容易把以下事件错误地当作能力完成：

- 看完一本书
- 看完一个视频
- 做完一个教程
- 把示例代码跑起来
- 知道一个问题的标准答案

这些事件只能证明“接触过”，不能证明“掌握”。

### 1.2 过早追求最短路径

结果导向型学习者常见模式：

```text
路线 A
  ↓
学到 20%
  ↓
发现路线 B 似乎更短
  ↓
切换
  ↓
发现路线 C 更接近本质
  ↓
再次切换
```

每次切换看起来都合理，但长期结果是没有任何一条路径被完整走穿。

LearningCI 不禁止优化路线，而是把“优化路线”限制到固定复盘日。

### 1.3 提前知道答案产生虚假完成感

真正的本质不是学习起点，而是大量事实、实验和经验被压缩后的结果。

如果一个人只记住：

> TCP 是可靠字节流。

但无法：

- 预测 recv 行为
- 实现 framing
- 分析重传
- 抓包诊断
- 设计新协议

那么这个“本质”并没有变成能力。

---

## 2. 核心思想：把学习当成 CI

软件工程：

```text
代码
→ 单元测试
→ 集成测试
→ Benchmark
→ Regression Test
→ CI PASS
```

LearningCI：

```text
知识节点
→ 解释测试
→ 预测测试
→ 实现测试
→ 诊断测试
→ 迁移测试
→ 延迟复测
→ PASS
```

因此问题从：

> 我是不是学会了？

变成：

> 测试通过了吗？

---

## 3. 三种分数必须分离

### 3.1 能力分

表示真正掌握程度。

它来自：

- 解释
- 预测
- 实现
- 诊断
- 迁移

### 3.2 执行分

表示是否按计划执行。

例如：

- 是否按时开始
- 是否完成当天唯一节点
- 是否绕开冻结路线
- 是否擅自跳过测试
- 是否把新兴趣放入 Parking Lot

执行分不能替代能力分。

### 3.3 项目分

表示能力在真实工程中的表现。

例如：

- Correctness
- Performance
- Reliability
- Architecture
- Debuggability
- Testability
- Documentation

三种分数绝不合并成一个“万能分数”。

---

## 4. 学习单位

LearningCI 的基本学习单位不是：

- 一本书
- 一章
- 一门课
- 一个视频

而是：

> 一个可以在数小时到 1～3 天内训练、测试和验收的最小能力节点。

例如：

错误节点：

- TCP
- Linux
- 分布式系统

合理节点：

- TCP 字节流与消息边界
- epoll LT/ET 行为差异
- WAL 的写入与恢复语义
- Kafka offset 与消费进度
- Raft leader election

---

## 5. 学习资料的定位

书籍、视频、博客、源码都只是“用于补足当前节点能力分”的资料。

不再建立：

> 看完书 = 学完技术

而是：

> 当前节点诊断只有 45 分 → 找资料补诊断能力。

---

## 6. 允许的浪费

LearningCI 明确允许探索成本。

学习未知领域时，不可能提前知道所有最短路径。

目标不是“0 浪费”，而是：

> 防止为了寻找 0 浪费而浪费更多时间。

建议默认接受：

- 70% 核心学习
- 20% 建立上下文
- 10% 事后发现价值较低

真正应该避免的是不断换路线而没有闭环。

---

## 7. 成功标准

LearningCI 成功不是“连续打卡 365 天”。

成功是：

1. 能力树逐渐变绿
2. 核心叶子节点达到 80+
3. 延迟复测后仍保持
4. 能力持续进入真实项目
5. 参考项目在正确性、性能、可靠性等维度达到明确标准
