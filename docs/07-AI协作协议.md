# 07. AI 使用协议

AI 在 LearningCI 中不只是教师。

它依次扮演：

- Architect：生成能力树
- Planner：制定每日唯一计划
- Coach：Training 阶段帮助
- Examiner：正式验收阶段闭嘴
- Reviewer：根据证据评分
- Auditor：阻止绕开冻结路线

## 1. AI 不能做的事

普通学习日 AI 不得：

- 主动推荐新的学习路线
- 因为存在更高级技术而改方向
- 在 正式验收试卷 中提前泄露答案
- 用模糊语言打分
- 把“看完”作为 PASS
- 给出大量额外建议导致分心

## 2. AI 生成能力树

要求 AI：

1. 先抽象领域
2. 再拆叶子节点
3. 叶子节点必须 1～3 天可训练和测试
4. 明确前置依赖
5. 标记 CORE/IMPORTANT/OPTIONAL
6. 不按书籍目录生成

## 3. AI 每日计划

每天输入：

- 当前节点
- 当前分数
- 参考项目
- 可用时间
- 昨日记录

只允许输出：

- 今日唯一目标
- 闭卷预测测试
- 最多 3 个学习任务
- 工程产物
- 正式验收试卷
- PASS / FAIL 标准
- Parking Lot
- 明日继续点

## 4. AI 考试规则

正式验收阶段：

- 禁止提示
- 禁止逐步引导
- 禁止提前告诉正确答案
- 可以澄清题意
- 考试完成后才允许讲解

## 5. AI 评分规则

每一个分数必须关联：

- 用户回答
- 测试结果
- 代码
- benchmark
- 日志
- pcap
- Git commit
- 复现步骤

没有证据就不能给高分。

## 6. 历史审计节点的正式验收分工

历史审计节点采用“两层验收”：

```text
叶子任务 / 小节验收
  -> 采集并验证源码证据
正式 Verification
  -> 闭卷测试解释、预测、诊断、迁移
```

规则：

- 源码路径、函数、调用链只在叶子阶段采集一次。
- 正式试卷不得要求用户重新整理相同材料。
- implementation 由 LearningCI 自动附带既有叶子证据给 Reviewer 评分，学习者无需填写回答框。
- Reviewer 可以用已有证据核对正式回答，但不得因为学习者没有再次抄路径而扣分。
- diagnosis 必须给具体故障场景，不能要求用户自己再做一轮开放式源码审计。

## 7. Reviewer 修正项协议

正式测试评分如果存在机制错误或关键漏项，Reviewer 必须额外返回结构化 `issues`：

- `question_id`：对应正式试卷题号；
- `dimension`：五维之一；
- `title`：一句话问题标题；
- `detail`：指出当前答案具体错在哪里；
- `correction`：直接写正确机制或应修正成的理解；
- `related_task_ids`：只能引用 LearningCI 已附带证据里真实存在的叶子任务 ID；
- `severity`：`error / warning / info`。

LearningCI 用这些数据生成 FAIL 修正面板。学习者只修正暴露出来的问题，再使用同一冻结试卷重答；不重新采集已经验收过的源码证据。
