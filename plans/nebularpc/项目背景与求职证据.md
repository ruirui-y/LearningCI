# 项目背景与求职证据

这个文件不是新的学习路线，而是给 LearningCI 节点细化和最终面试作品化提供背景。

## 1. DemandStation —— 生产实战主证据

仓库：`https://github.com/ruirui-y/DemandStation.git`

当前背景（由项目作者提供）：

- 已有十余台客户购买并运行；
- 服务端长期运行，当前没有发生过进程崩溃事故；
- 生产主要部署在 Windows Server；
- 项目能够在 Linux 编译，但现有生产环境没有迁移；
- 不迁移的主要工程原因是现有 Windows 上已经稳定配置 MySQL 与 Redis，没有为了“技术看起来更高级”承担无必要迁移风险。

面试时这个项目重点证明：

- 真正把系统交付给客户，而不是只写 Demo；
- 长期运行、升级、配置、故障处置、兼容性等工程问题；
- Windows / Linux 选择背后的成本与收益判断；
- MySQL / Redis / 服务端进程之间的真实部署关系。

需要逐步补齐的可验证材料：匿名客户数量、部署拓扑、版本记录、运行日志、真实故障案例、升级/回滚过程。

## 2. MyMuduo —— Linux 网络与底层能力证据

仓库：`https://github.com/ruirui-y/MyMuduo`

公开仓库包含 Reactor / One Loop Per Thread、epoll、eventfd、TcpConnection、TcpClient、Buffer、Timer、异步日志等实现。README 还记录了性能数据与生产使用描述。

面试时不直接把 README 数字当结论，而要准备：

- 具体源码文件与函数调用链；
- 可复现的 benchmark 命令和原始数据；
- partial write / EPOLLOUT / 生命周期等异常路径；
- 为什么采用当前线程所有权和 Buffer 设计；
- 哪些历史实现后来被 NebulaRPC 重新验证或改进。

## 3. game_rpc_project —— 旧 RPC 历史断点证据

仓库：`https://github.com/ruirui-y/game_rpc_project`

它的意义不是作为最终作品，而是证明 RequestId / PendingCall / promise-future / ReceiverThread 等旧模型真实存在，并为 NebulaRPC 的 Event-Driven Async RPC 提供历史断点。

## 4. NebulaRPC —— 系统深度主项目

NebulaRPC 是本 LearningCI 主线的核心目标项目。

它负责把已有网络/RPC经验推进到：

- Event-Driven Async RPC；
- C++20 Coroutine；
- Exactly-Once Completion；
- Multi-Reactor ownership；
- Backpressure / bounded resources；
- Observability / Reliability / Fault Injection；
- perf / FlameGraph / framework benchmark。

最终面试中它承担“系统深度”的主要证明责任。

## 5. OmniBox —— 系统广度辅助证据

仓库：`https://github.com/ruirui-y/OmniBox`

公开仓库包含 Qt6 C++ 客户端、UDP 设备发现、文件管理、Protobuf、自研 RPC、多个后端服务和 MySQL 等组成部分。

它适合作为：

- 客户端 + 服务端完整系统设计；
- 微服务边界；
- 文件传输；
- 自研通信组件在真实业务中的使用；
- Qt/C++ 工程能力

的辅助证明，不再作为“无限加入新技术”的沙盒主线。

## 6. 四项目的面试分工

```text
DemandStation  → 真实生产 / 客户 / 交付 / 运维
MyMuduo        → Linux 网络底层 / Reactor / Buffer / 性能
NebulaRPC      → 现代异步 RPC / 协程 / 可靠性 / 性能工程
OmniBox        → 客户端 + 微服务 + 文件传输的系统广度
```

最终面试中不追求“我有很多项目”，而要让面试官看到：

> 同一个人既做过真实生产交付，也能深入网络底层，还能把异步 RPC、并发状态机、可靠性和性能工程做成可复现证据。
